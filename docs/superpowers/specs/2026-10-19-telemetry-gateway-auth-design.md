# QMS 遥测采集接口网关认证设计

## 背景与目标

飞针机采集器已将现场记录保存在独立的本地待发送队列中。现场 QMS 运行在 `http://192.168.1.98:8080`，遥测 POST 返回 HTTP 401：采集器已配置网关令牌，但没有 Bearer Token。QMS 当前生产安全链要求该接口先通过 Bearer JWT，控制器随后校验 `X-Gateway-Token`。静态 Bearer Token 到期后仍会中断长期采集。

目标是让飞针机采集器使用现有网关令牌持续上报，无需保存 QMS 用户名、密码或定期手动更换 Bearer Token。已入队事件继续按现有 `recordNo` 幂等机制重试。用户确认只对遥测采集 POST 增加网关认证，并保持其他接口的鉴权规则。

## 认证与租户边界

仅 `POST /api/v1/equipment/telemetry` 支持无 Bearer 的网关请求。QMS 使用已有 `QMS_GATEWAY_SHARED_TOKEN` 与请求头 `X-Gateway-Token` 做恒定时间比较；缺失或错误令牌返回 401，不进入控制器或数据库。不能凭请求体中的 `username`、`machineName` 或客户端传入的租户头决定租户。

网关请求的租户由新的服务端配置 `QMS_GATEWAY_TELEMETRY_TENANT_CODE` 指定。配置缺失时网关模式关闭并返回 HTTP 503；租户不存在或非 ACTIVE 时返回 HTTP 403。鉴权和租户检查成功后，QMS 为本次请求建立租户上下文，调用现有设备网关映射和遥测服务，并在 `finally` 中清除上下文。设备映射仍按该租户查询，现有载荷验证与 `recordNo` 幂等行为不变。现场 QMS 当前仅列出一个可登录租户；配置仍显式指定租户，不从“唯一租户”推断。

若请求带 Bearer，继续使用现有 JWT 校验和 JWT 的 `tenant_code` 声明，且控制器仍要求有效 `X-Gateway-Token`。无效或格式错误的 Authorization 头直接按现有 Bearer 认证失败处理，不回退到网关模式。遥测 GET、其他 QMS API 和其他网关接口继续要求现有认证。开发模式保留现有开发租户上下文与网关令牌校验，不改变其行为。

## 采集器与配置

飞针机采集器继续发送原有 JSON 和 `X-Gateway-Token`，`BearerToken` 留空即可，无需修改 EXE、队列格式或历史格式。若 QMS 仍返回非 2xx，采集器保持事件在本地队列并记录失败；QMS 更新后按既有轮询重试，成功记录先持久化再出队。配置和日志不得输出真实网关令牌。

QMS 的 Windows 部署示例、Docker 本地部署示例和说明文档增加 `QMS_GATEWAY_TELEMETRY_TENANT_CODE`。实际部署时在 QMS 服务器的私有环境配置中设置该值，并确认已有 `QMS_GATEWAY_SHARED_TOKEN` 与采集器一致；不能把现场令牌写入版本库。未设置新租户配置的现有部署维持原有 JWT 路径。

## 网络与部署

现场目前只有 HTTP。网关令牌在该链路上传输时没有加密，需将 8080 入站访问限制到采集电脑或受控内网来源，并安排后续 HTTPS。网关认证不能扩展为全站免登录，也不能通过客户端提供的租户编码切换租户。

发布 QMS 后重启 `192.168.1.98` 上的 QMS 服务。采集器无须重建；保持其 `BearerToken` 为空。用一条现有待发事件验证 QMS 返回 2xx、同步历史写成功、待发数量下降，并在 QMS 对应租户确认记录。若部署回退，采集器继续留存未成功事件；重复发送由现有 `recordNo` 幂等处理。

当前 QMS 工作目录存在其他未提交修改，包括安全配置文件。实施时需保留这些修改，隔离本任务的改动并核对最终差异；不能覆盖或提交无关文件。

## 验证范围

- 无 Bearer 且网关令牌正确、租户配置有效时，遥测 POST 使用配置租户写入并返回 2xx。
- 缺失或错误网关令牌、缺失租户配置、停用租户均拒绝请求；没有写入或跨租户查询。
- 有效 Bearer 加网关令牌仍可按 JWT 租户上报；无效 Bearer 不回退到网关模式。
- 遥测 GET 和其他 QMS 路径不能只凭网关令牌访问。
- 本地端到端测试覆盖采集器现有空 Bearer 请求、失败留队、成功出队；验证日志和历史不含令牌。

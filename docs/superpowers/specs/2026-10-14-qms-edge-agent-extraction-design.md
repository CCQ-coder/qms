# QMS Edge Agent 仓库抽离设计

**状态：** 已确认，待迁移计划批准  
**日期：** 2026-10-14

## 目标与范围

将 QMS 中面向现场设备的监听器抽离为独立 Git 项目 `qms-edge-agent`，由其独立构建、发布和维护。新项目远程地址为 `https://github.com/CCQ-coder/qms-edge-agent.git`，远端默认分支为 `main`，且已有初始提交。

本次是低风险的仓库抽离，不重写监听器实现，也不改变现场兼容行为。迁移后的唯一监听器源码在新仓库；QMS 中原路径保留迁移说明，不保留可维护的镜像源码。

本次包含：

- 从 QMS 当前工作区迁移精德、森泉、科视设备监听器的源码、构建脚本、脱敏默认配置和部署文档。
- 建立独立项目的忽略规则、版本记录和 QMS Telemetry v1 接入说明。
- 保留构建、配置、设备协议和本地持久化队列的既有行为。
- 在成功推送新仓库且验证通过后，将 QMS 原监听器目录替换为指向新仓库的迁移说明。

本次不包含：

- 将 .NET Framework / WinForms 迁移到现代 .NET、Windows Service 或新的安装技术。
- 修改 QMS 的遥测接口、数据库、设备映射、认证方式或业务逻辑。
- 迁移 `gateway/` 下的 Spring Boot ERP 工单同步网关。
- 修改任何现场计算机、已发布 EXE、INI 文件或待发队列。
- 将每个设备厂商协议拆成独立代码仓库。

## 已确认的约束

- 新项目本地目录为 `D:\project\qms-edge-agent`，与 `D:\project\qms` 并列。
- 新项目是监听器的唯一源码；QMS 旧目录只保留迁移说明和新仓库地址。
- 首版优先保持 Windows、WinForms、INI 配置、命令行参数、监听端口和安装方式不变。
- 迁移以当前工作区文件为准，不能使用 Git 历史覆盖当前未提交的监听器修改。
- 远端已有 `main` 分支，因此迁移以克隆该仓库为起点，不初始化仓库、不改写远端历史。

## 架构与职责边界

```text
现场设备
  │ 精德 / 森泉 / 科视 HTTP 协议
  ▼
qms-edge-agent（Windows 现场中间机）
  ├─ 协议监听与协议响应
  ├─ 事件归一化
  ├─ 本地持久化队列、重试、日志与图形监控
  └─ QMS Telemetry v1 客户端
        │ HTTPS / HTTP
        ▼
QMS
  ├─ 遥测接收、鉴权与幂等处理
  ├─ 设备映射和租户归属
  └─ 数据留存、状态、告警和报表
```

`qms-edge-agent` 是现场 Edge 应用，负责设备协议适配和可靠转发。QMS 是控制面和业务系统，负责接收与处理已归一化的遥测事件。

Edge Agent 不读取 QMS 数据库、不引用 QMS 后端源码、不假设 QMS 与设备处于同一网络。QMS 不构建、打包或发布 Edge Agent。

多个设备协议仍属于同一个 Edge Agent 项目，复用本地队列、配置、认证、日志、重试和运维能力；后续只有在某一协议拥有独立交付节奏、定制团队或运行环境时，才评估进一步拆分插件或发行包。

## 新仓库结构

```text
qms-edge-agent/
  src/
    JingdeEapForwarder.cs
  config/
    JingdeEapForwarder.ini
  scripts/
    build.cmd
    start-gateway.cmd
    install-autostart.cmd
  docs/
    README.md
    qms-telemetry-contract.md
  .gitignore

```

首版允许单个 `JingdeEapForwarder.cs` 原样迁入。该文件内部模块化、目标框架升级、安装包与自动更新能力属于后续独立改造，不能与仓库抽离混合实施。

`.gitignore` 必须排除编译 EXE、构建目录、日志、`data/pending-events.json`、现场 INI 覆盖文件、令牌和其他运行时产物。受版本控制的 INI 只能包含占位令牌，不能包含现场凭据。

## QMS Telemetry v1 契约

抽离后的第一个版本保留现有接口约定：

| 项目 | 契约 |
| --- | --- |
| URL | `POST {QmsBaseUrl}/api/v1/equipment/telemetry` |
| 请求体 | `{ "events": [...] }` |
| 认证 | `X-Gateway-Token` |
| 成功判定 | 任意 HTTP `2xx` |
| 幂等 | QMS 以设备事件的稳定记录号处理重复上报 |
| 队列删除 | 仅在 QMS 成功响应后删除已确认批次 |

QMS 是此服务端契约的权威所有者。Edge Agent 仓库保留固定版本的接入说明和自动兼容测试；该说明用于消费和校验契约，而不是创建第二个独立的服务端定义。

首版兼容以下 Edge Agent 外部行为：

- `JingdeEapForwarder.ini` 的键名及默认值。
- `--headless`、`--self-test` 和 `--config` 命令行参数。
- 精德、森泉、科视的监听端口、HTTP 路由、请求验证和响应结构。
- 设备接收成功响应的条件：事件已安全写入本地队列，而非 QMS 已经处理。
- `pending-events.json` 的恢复、重试和成功后删除语义。
- Windows `build.cmd`、`start-gateway.cmd` 和 `install-autostart.cmd` 的使用方式。

全局共享令牌继续兼容保留。按网关签发、撤销与轮换凭据是后续安全演进，不属于本次抽离。

## 迁移步骤

1. 克隆远端 `main` 到 `D:\project\qms-edge-agent`，保留已有的远端初始提交。
2. 记录 QMS 当前监听器源文件和默认配置的哈希与迁移清单。
3. 将当前工作区中的监听器源码、脚本、脱敏配置和部署文档迁入新仓库；不得以 HEAD 或旧构建产物替代它们。
4. 在新仓库补充忽略规则、版本记录、安装文档和 Telemetry v1 接入说明。
5. 用既有 `build.cmd` 构建，并执行 `JingdeEapForwarder.exe --self-test`。
6. 比对迁移前后的源文件和默认配置哈希，确认它们未被意外改写；构建、启动和安装脚本仅允许为新目录结构调整相对路径，部署文档仅允许更新仓库名、项目路径和构建输出路径，并对这些预期改动进行人工审查。
7. 检查受控文件中没有真实令牌、日志、待发队列或输出产物。
8. 创建新仓库的首个迁移提交，添加标签 `v1.0.0-extracted`，并推送 `main` 与标签到指定远端。
9. 只有远端推送和上述验证全部成功后，才用迁移说明替换 QMS 中的旧监听器目录；该说明必须包含新仓库地址、首个标签和 Telemetry v1 兼容范围。
10. QMS 的 ERP 工单同步网关及遥测后端不作任何变更。

## 验证与验收

迁移完成需满足：

1. 新仓库可以通过现有 .NET Framework 编译器和 `build.cmd` 构建 EXE。
2. 新 EXE 的 `--self-test` 退出码为 `0`。
3. 迁移的 C# 源文件和默认配置与迁移前工作区哈希一致；构建、启动和安装脚本的差异仅为适配新目录结构的相对路径改动，部署文档的差异仅为更新仓库名、项目路径和构建输出路径。
4. 受控默认配置不含真实凭据；运行时文件均被忽略。
5. 文档覆盖首次部署、配置、日志位置、本地队列恢复和与 QMS 契约。
6. 新仓库 `main` 已包含迁移提交和 `v1.0.0-extracted` 标签。
7. QMS 中只存在迁移指引；ERP 同步网关与 QMS 遥测服务代码没有因为此次迁移而变化。

现场验收不属于本次仓库抽离；因没有修改现场发布包或 QMS 行为，本次不应导致现场停机或队列丢失。

## 回滚

- 在新仓库推送成功之前，QMS 中原监听器源码保持完整，任何错误均可直接停止。
- 未操作现场机器的 EXE、INI、日志或队列，因此仓库迁移失败不影响生产上报。
- 推送成功后，新仓库的 `v1.0.0-extracted` 是可复现的回退点。
- 若 QMS 占位说明需要撤回，可从新仓库该标签恢复对应源码；不能重新建立两个并行维护的源码副本。
